Step 9 — Key finding
dto received: [Function: anonymous]
The log printed [Function: anonymous] instead of { email: '...', password: '...' }. NestJS's @Body() decorator uses TypeScript's emitDecoratorMetadata to know the parameter type. It was receiving Function (anonymous) as the type — meaning the class reference was erased at compile time.
Step 10 — Root cause identified
Inspected compiled dist/src/auth/auth.controller.js
The compiled output confirmed the issue: 
__metadata("design:paramtypes", [Function])
Instead of the expected: 
__metadata("design:paramtypes", [login_request_dto_1.LoginRequestDto])
Cause: auth.controller.ts imported the DTO as import type. TypeScript erases type imports completely at compile time — so no class reference is available for emitDecoratorMetadata to emit.
Step 11 — ROOT CAUSE FIX ✓
Changed import type → import in auth.controller.ts
Changed: 
import type { LoginRequestDto } from './dto/login-request.dto';
To: 
import { LoginRequestDto } from './dto/login-request.dto';
Now TypeScript emits the real class reference in metadata, and @Body() can correctly deserialize the JSON request body into a LoginRequestDto instance.

3. Root Cause Explanation

NestJS's @Body() decorator relies on TypeScript's emitDecoratorMetadata feature to know what class to instantiate when deserializing a request body. When a DTO is imported with import type, TypeScript treats it as a type-only import and completely erases it from the compiled JavaScript output. At runtime, the parameter type metadata becomes [Function: anonymous] — a generic function placeholder — and NestJS cannot use it to deserialize the body, resulting in an empty object where all fields are undefined.

Rule for this codebase: Any DTO class used in a controller parameter decorated with @Body(), @Param(), or @Query() must be imported with a regular import, never import type. Return type DTOs (used only as type annotations on return values) are safe to import as import type.
